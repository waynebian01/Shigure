## 项目简介

Shigure 是一个 Windows WinForms 桌面程序。它从目标窗口读取 Fuyutsui 绘制的像素状态，按职业 keymap 和模块规则选择按键，并在界面中展示状态、光环、技能、队伍、动态单位、逻辑结果和运行日志。

程序采用单实例运行；再次启动时会提示“Shigure 已经在运行”，随后退出新实例。

当前版本：`1.2.1.31`

## 主要功能

- 扫描最多 1020 格的顶部状态行和队伍治疗吸收数据；可选择支持窗口遮挡的 Windows 图形捕获（WGC）或原版屏幕截图。
- 按职业、专精、队伍类型和英雄天赋自动匹配模块，也可手动锁定符合条件的模块。
- 使用可视化编辑器维护规则、主/子条件、动态单位、数量字段、条件动态数值和公式动态数值。
- 以对应版本的内置插件目录为权威源编辑职业配置与宏，并按 SHA-256 将插件部署到所选游戏目录及已运行游戏的 `Interface\AddOns\{插件名}`。
- 支持 `switch`、`click`、`hold` 三种触发模式，以及除 `ALT` 外的键盘按键、`XBUTTON1`、`XBUTTON2`。

## 界面

- 置顶浮动条：显示程序名、当前职业图标颜色和逻辑状态，提供 `开启/关闭`、`设置`、`✕` 按钮。窗口可拖动和缩放，显示后自动启动运行循环。
- `通用`：顶部可手动选择 `Retail Fuyutsui`、`Forever Shingen` 的配置编辑界面，或让编辑界面自动跟随前台游戏；选择会保存到本机设置，不改变运行游戏与插件的绑定。游戏版本卡片还可分别选择正式服和无限服的游戏 `.exe` 文件作为固定插件部署目录，不限制文件名。还可设置触发键、发送模式和画面捕获方式；“性能”区域可分别调整画面扫描和模块规则计算的间隔；更新界面所选版本的配置并同步对应游戏；当前模块和默认模块设置始终对应运行中的游戏；从 GitHub 按需下载或更新技能/物品图标数据包。WGC 是默认方式，游戏窗口被其他窗口遮挡时仍可读取；窗口最小化或捕获停止时会暂停扫描。原版方式读取显示器实际画面，因此会受到遮挡影响。
- `配置`：直接编辑界面所选版本插件 `class/*.lua` 中的 `ClassBlocks`，包括状态、光环、冷却（技能冷却与当前专精物品冷却）和队伍字段；启用队伍时生命值与职责固定开启，驱散、职业可选；玩家、目标、焦点、首领1–5及姓名板光环可用“玩家施放”控制是否追加 `PLAYER` 筛选，首领1–5只配置敌对减益，未勾选（或 Lua 中省略 `isPlayer`）时为 false；技能列表页可编辑 `spellsList` 中索引 1–100 的法术 ID、索引和名称，也可从技能数据库添加；物品列表页编辑职业级 `itemsList`（`[itemId] = { index, name }`，允许同名、禁止同 ID），并可从全量物品数据库添加。旧版稀疏索引格式只读，需先迁移到 `states/auras/spells/items/group` 格式。
- 队伍和姓名板光环的 `maxApps` 为正数时，剩余时间格后紧邻增加一格层数像素，蓝通道以整数 `0–255` 编码层数；每个这样的光环为 40 个单位额外占用 40 格。队伍字段 `auras.<spellId>.apps` 和姓名板字段 `nameplates.<槽位>.auras.<spellId>.apps` 可用于普通数值条件；队友及敌人数量条件中的光环筛选仍使用剩余时间。队伍或姓名板布局超过主像素行 1020 格上限时会停用对应区域。
- 队伍与姓名板状态列表按字段分列：队伍展示生命值、治疗吸收、职责、职业、驱散；姓名板展示生命值、距离、战斗、TTD、仇恨值、施法技能。强化锁喉列仅在当前运行配置启用该字段时显示（正式服奇袭），切换职业、专精或关闭配置后自动隐藏；没有可见敌人时仍按配置保留该列。未配置或无数据的字段显示 `-`，光环及其余字段集中在末列。
- 姓名板 TTD（预计死亡秒数）由 Shigure 根据整数生命百分比计算：优先对最近 5 秒样本做线性回归，无法得到净掉血趋势时依次扩展到 10、15 秒；样本跨度至少 1 秒。掉血速度采用 2 秒时间常数的指数平滑，TTD 为当前生命百分比除以平滑速度并向上取整。暂时无法估算时最多沿用上次速度 3 秒，姓名板消失、死亡或扫描失败立即清空。姓名板状态页固定显示 TTD 列，没有估算时显示 `null`；未知 TTD 的模块条件不命中。目标、焦点和首领 TTD 共用映射姓名板的结果。
- “特殊”状态中的“倒数”监听玩家倒计时事件：开始时显示剩余秒数并每秒减 1，取消或归零时显示 0。
- 正式服“特殊”状态中的“强化锁喉”显示剩余整数秒（向上取整）：潜行中或脱潜后 6 秒内成功施放锁喉（703），在当前剩余时间上增加 24 秒，最高 32 秒，到期归零。默认奇袭配置已启用此字段。
- 正式服“特殊”状态中的“目标强化锁喉”使用 AuraContainer 原生图标槽显示当前目标身上**自己施放**的锁喉减益（`HARMFUL|PLAYER`、703）：强化锁喉图标 `7195162` 输出 `1`，普通锁喉图标 `132297` 输出 `2`，无自己的锁喉时输出 `0`。不枚举光环、不读取或比较保密图标 ID；默认奇袭配置已启用此字段。数值由替换图标的顶部横条绘制，Lua 状态 getter 仅提供 `0` 底色。
- “姓名板”页提供可勾选的“仇恨值”，默认关闭。启用后每个姓名板追加一格（共 40 格），读取 `UnitThreatSituation("player", unit)`：`0=未坦克、1=仇恨高但未坦克、2=坦克但仇恨不稳、3=稳定坦克`，返回 `nil` 时按 `0` 处理。可用 `nameplates.<槽位>.仇恨值` 或敌人数量/敌人平均血量筛选的“仇恨值”进行比较（例如 `>= 2`）。开关随配置和模块依赖保存，导入保留已有本地开关；旧状态字段“敌人数量”“敌人数-无仇恨”“敌人数-有仇恨”已移除，改用姓名板动态数量。
- “目标”“焦点”以及可选的“首领1–5”状态可配置“施法技能”：相邻两格分别定位和显示 `UnitCastingInfo` 或 `UnitChannelInfo` 的原始 `spellID`，无施法时为 `0`。目标、焦点字段默认加入所有职业专精。姓名板页的同名开关默认关闭；勾选后为每个可见敌对姓名板槽位增加两格（40 槽共 80 格），提供 `nameplates.<槽位>.施法技能`。定位格编码索引与主色条容量，数据格以完整 RGB 编码 `0–16777215`，可直接用 `== 123456` 等数值条件比较。
- 正式服奇袭的“姓名板”页提供独立“强化锁喉”卡片，默认启用；Lua `nameplates.improvedGarrote` 省略时默认开启，明确 `false` 时关闭，其他专精及永久服不启用。每个姓名板在全部光环及层数字段后追加一格（总计增加 40 格），通过同一原生图标槽输出自己锁喉的 `0=无、1=强化、2=普通`。字段 `nameplates.<槽位>.强化锁喉` 可用于普通条件、敌人数量及敌人平均血量筛选，与 `nameplates.<槽位>.auras.703.value` 的剩余时间独立。开关随配置和模块依赖快照保存，导入保留本地已有开关；本地没有姓名板配置时才采用模块携带的开关。
- 两个替换纹理位于 `Retail/Interface/ICONS/`：`Ability_Rogue_Garrote.tga`（普通，顶部 RGB `255,255,2`）和 `INV12_Ability_Rogue_Garrote_Empowered.tga`（强化，顶部 RGB `255,255,1`）。来源为 [Clean Icons 12.1.0.69299-V5-1](https://github.com/AcidWeb/Clean-Icons-Mechagnome-Edition/releases/tag/12.1.0.69299-V5-1)，尺寸为 128×128，视觉顶部第 0–3 行的不透明横条为 128×4，横条外内容保持源文件不变。原生 Texture 使用 TOP 锚点铺满色格，仅采样顶部横条内部的 2×2 区域（裁切坐标 63/128、65/128、1/128、3/128），以固定顶点颜色保留色格索引。实际截图颜色、资源覆盖和战斗安全性需在游戏内验证。
- 打开 Shigure 时的正式服同步及“更新配置”的全量同步会将这两个纹理部署到游戏的 `Interface/ICONS/`（不是 `AddOns`），前提是已设置有效的正式服游戏路径或能检测到对应游戏进程。文件内容相同则跳过复制；启用/暂停切换不会额外触发同步。覆盖已有同名文件前，首次备份为 `<文件名>.shigure-original`，后续更新保留该备份；同步失败会显示具体文件和原因。替换会影响游戏内所有使用这些资源的位置，首次安装或纹理更新后必须**完全退出并重新启动游戏**。如需恢复，退出游戏后移走两个替换 TGA；若有备份，将 `.shigure-original` 文件恢复为原名，再启动游戏。
- 安装并启用 EXBoss 时，“特殊”状态可添加“EX首领技能类型”“EX首领技能事件”“EX首领技能倒计时”三个像素字段。类型输出 `0=无/未知、1=其他、2=坦克、3=治疗、4=点名、5=机制、6=特殊`；事件将 EXBossData 的全部唯一 `eventID` 按数值升序组成表并输出其一基键（当前 247 项，范围 `1–247`）；倒计时输出距离下一条 EXBoss 技能预计施放的整数秒（向上取整并限制为 `0–255`）。三个状态均按像素协议除以 `255` 后绘制，Shigure 扫描后还原为整数。Fuyutsui 会从 EXBoss 的固定 AI 调度/完成事件维护完整倒计时，并用通用“五秒剩余”事件兼容其它可提供稳定 `eventID` 的计时器；未安装 EXBoss 时三项保持为 `0`。
- 同一分类还可添加“EX小怪技能类型”“EX小怪技能事件”“EX小怪技能倒计时”。类型编码与首领一致；事件将 `EXBOSS_TRASH_CD_DATA` 的唯一 `spellID` 按数值升序组成独立的一基键表（当前 136 项，范围 `1–136`），不会占用或改变首领事件键。小怪计时来自 EXBoss 的小怪 CD 五秒通知，并在观察到对应技能开始施法时及时移除；多个小怪事件同时存在时输出倒计时最近的一项。未安装 EXBoss 时三项保持为 `0`。
- 团队首领战优先使用 BigWigs 时，可添加“BigWigs首领技能类型”“BigWigs首领技能事件”“BigWigs首领技能倒计时”三个像素字段。类型输出 `0=无/未安装、1=精确计时、2=近似CD、3=点名计时、4=施法计时、5=即时警告`；事件使用当前 BigWigs 团本模块的数字技能键目录（193 项，按 `spellID` 升序分配 `1–193`）；倒计时输出当前最近事件的剩余整数秒并限制为 `0–255`。桥接仅接收 `raid` 场景，排除 LittleWigs 与小怪模块；未安装 BigWigs 时三项保持为 `0`，不会影响 EX 字段。
- `宏`：编辑界面所选版本插件 `core/classmacros.lua` 中各职业的职业级动态宏、静态宏和特殊宏。动态宏每项占用 40 个团队点名槽位；特殊宏的技能名必须手工填写，不从宏正文解析，生成映射时固定为无目标、无宏条件。
- `模块`：新建、编辑、删除本地模块，维护作者、推荐天赋、匹配条件、动态字段和有序规则。规则支持拖拽、上移、下移、复制与插入。
- `状态`：分栏显示基础状态、`auras`、`spells` 和模块计算出的动态单位/数值。
- `队伍`：显示 `group` 中当前队伍成员及扫描字段摘要。

### WGC 无黄色提示边框

Windows 的正式无边框捕获流程要求程序具有包身份、在包清单声明无边框能力，并由用户授权。Shigure 使用“外部位置（稀疏）MSIX”只提供身份，程序文件仍保留在普通可写目录，不改变现有配置和插件文件的读写方式。

开发机首次配置：

```powershell
.\Packaging\New-DevelopmentCertificate.ps1
.\Packaging\Build-SparsePackage.ps1 `
  -CertificatePath .\artifacts\certificate\Shigure.Development.pfx `
  -CertificatePassword Shigure-Development-Only `
  -Register
```

需要安装 Windows SDK 的 MSIX Packaging Tools（`MakeAppx.exe` 与 `SignTool.exe`）。注册完成后，从脚本输出的 `artifacts\sparse-package\publish\Shigure.exe` 启动，并在 Windows 首次弹出的授权窗口中允许无边框捕获。开发证书仅供本机测试；正式发布必须使用主题为 `CN=Arasaka Corporation` 的可信代码签名证书。直接运行 `dotnet run` 没有包身份，系统仍可能显示黄色边框。

## 运行

在仓库根目录执行：

```powershell
dotnet run --project .\Shigure.csproj
```

可选启动参数：

```powershell
dotnet run --project .\Shigure.csproj -- --toggle XBUTTON2 --mode switch --logic-ms 100 --render-ms 100
```

- `game_profiles.json`：为每个游戏进程指定插件。当前 `Wow`、`WowT` 使用 `Fuyutsui`，`WowClassic` 使用 `Shingen`；进程名可带 `.exe`。程序选择 Windows Z 顺序中最靠前的候选可见窗口，前台游戏改变后会切换运行所用插件、配置、键位和模块。缺少此文件时启动会报错。
- `--toggle`：触发键，默认 `XBUTTON2`。
- `--mode`：发送模式，支持 `switch`、`click`、`hold`。
- `--logic-ms`：初始逻辑计算间隔，默认 `100` ms，最小 `50` ms；通用页保存的性能设置会在后续启动时覆盖它。
- `--render-ms`：UI 刷新间隔，默认 `100` ms，最小 `100` ms。

发送模式：

- `switch`：按一次开启，再按一次关闭。
- `click`：每次按下只执行一轮逻辑。
- `hold`：按住时运行，松开后停止。

程序会直接从当前 EXE 所在目录运行。Retail 文件集中在 `Retail/`（`Fuyutsui/`、`config/`、`keymap/`），Forever 文件集中在 `Forever/`（`Shingen/`、`config/`、`keymap/`）。Fuyutsui 模块位于 `{MyDocuments}/Shigure/module`，Shingen 模块位于 `{MyDocuments}/Shigure/module-Shingen`；UI 缓存位于 `{MyDocuments}/Shigure/cache`。

## 构建

```powershell
dotnet build .\Shigure.csproj
```

## 游戏版本与配置同步

在 `game_profiles.json` 中按进程填写版本目录和插件目录名，例如：

```json
{
  "profiles": [
    { "process": "Wow", "version": "Retail", "addon": "Fuyutsui" },
    { "process": "WowT", "version": "Retail", "addon": "Fuyutsui" },
    { "process": "WowClassic", "version": "Forever", "addon": "Shingen" }
  ]
}
```

前台游戏为 `WowClassic` 时，运行逻辑使用 `Forever/Shingen/` 的配置、键位和模块。通用页顶部可选择要编辑的版本，选择会保留到下次启动；按“自动”让编辑界面跟随前台游戏。手动切换界面不会改变运行版本，也不会触发部署或重启。切换前如有未保存的配置、宏或模块，先保存或放弃修改；前台游戏变化仍可切换运行版本。修改 `game_profiles.json` 后重启 Shigure。`dotnet run --project .\Shigure.csproj -- --update-config` 与 `--update-keymap` 会分别为两套插件生成 JSON。

项目中的插件目录是各自版本的权威源。`通用` 页的“更新配置”会读取界面所选版本：

- `Retail/Fuyutsui/class/*.lua` → `Retail/config/*.json`
- `Retail/Fuyutsui/core/classmacros.lua` → `Retail/keymap/*.json`
- `Forever/Shingen/class/*.lua` → `Forever/config/*.json`
- `Forever/Shingen/core/classmacros.lua` → `Forever/keymap/*.json`

如果运行版本目录的 `config/` 或 `keymap/` 缺失或文件不完整，启动 Shigure 时会先从对应插件源文件自动补齐；新建 `config/` 时也会生成运行时必需的 `common.json`。手动保存或更新时使用界面所选版本，刷新对应模块编辑器的字段/keymap；仅当它也是运行版本时重启运行循环。通用页“游戏版本”卡片可分别选择对应版本的游戏 `.exe` 文件，只检查扩展名和文件是否存在，不限制文件名；路径会保留到下次启动，只选择路径不会立即同步。游戏运行时的进程识别仍使用 `game_profiles.json` 中的 `process`。插件会同步到所选目录，以及所有正在运行且映射到该版本的游戏目录，重复目录只同步一次；例如 `Wow` 与 `WowT` 同时运行时，Retail/Fuyutsui 会部署到两处不同目录。所选游戏未运行时仍可点击“更新配置”部署。已保存路径失效时会提示并跳过该目录，其他目录继续同步。未选择路径且未找到对应游戏时保留本地保存结果。部署只复制缺失或 SHA-256 不同的文件，保留游戏目录中的额外文件。

`配置` 页和 `宏` 页保存时先写入项目内 Lua、重新生成 config/keymap，再只把当前修改的 Lua 文件部署到游戏目录。找不到目标目录或目标文件不可写时，本地保存不会回滚；界面和日志会提示游戏同步未完成，可选择游戏程序路径后再次点击“更新配置”。

### 插入法术与插入物品命令

游戏内可使用 `/fu i 技能名称或spellId` 临时写入“插入法术”状态。例如 `/fu i 奥术洪流` 保留按名称查询，`/fu i 232633` 则直接按 spellId 精确读取当前 `Fuyutsui.spellsList` 中的本地序号。该命令只检查 `spellsList`，不检查 `ClassMacros`，也不接受 `target`、`player` 等单位参数；成功后聊天框会显示技能名称、spellId 和本地序号。

同样可用 `/fu t 物品名称或itemId` 临时写入“插入物品”状态。例如 `/fu t 鲁莽药水` 按名称查询，`/fu t 241288` 则按 itemId 精确读取当前 `Fuyutsui.itemsList` 中的本地序号。该命令只检查 `itemsList`，不检查 `ClassMacros`；成功后聊天框会显示物品名称、itemId 和本地序号。模块规则中的 `自动插入物品` 会读取该状态并映射到 keymap 中的物品宏。

### `config` 结构

`config` 描述如何把像素数据翻译成运行时状态。字段对象包含：

- `step`：顶部状态行的列索引，支持 `1`～`1020`；旧配置中的特殊值 `"bar"` 仍可读取旧版左侧计数条。
- `type`：字段类型，支持 `int`、`bool`、`string`。

顶部状态行由 Fuyutsui 绘制，容量按当前专精实际占用分档：默认 510 格，超过 510 升到 765，再超过 765 升到 1020（1020 是上限，再超出则停用姓名板）。每格宽为屏幕宽度除以「当前档位 + 1」。

Shigure 按四套颜色方案解码，红通道是方案序号、绿通道是套内序号、蓝通道 `b` 是该 `step` 的原始值：

| `step` | 红通道 | 绿通道 |
| --- | --- | --- |
| `1`～`255` | `0` | `i / 255` |
| `256`～`510` | `1 / 255` | `(i - 255) / 255` |
| `511`～`765` | `2 / 255` | `(i - 510) / 255` |
| `766`～`1020` | `3 / 255` | `(i - 765) / 255` |

当前档位的最后一个数据格之后还有一格恒定纯红 `(1, 0, 0, 1)` 的终止色块；Shigure 扫到红色即结束本次主色条扫描，因此不需要知道插件当前用的是哪个档位。数据格的绿通道恒大于 0，不会与终止色块混淆。法术充能数与施法次数的 `.count` 格紧邻对应技能最后一个冷却格；旧计数条行不再绘制。治疗吸收网格启用时，Shigure 通过首槽前锚点定位网格。

治疗吸收网格最多 40 条，每行 20 条、共两行。每条由前锚点、25 格条身和终点格组成；条身背景的绿通道为 `1`～`25`，终点格为 `26`，蓝通道标识单位。Shigure 读取白色填充右侧的第一格，以 `(绿通道 - 1) × 4` 得到 `0`～`100` 的治疗吸收百分比（每档 4%）；填满时由终点格读出 `100`。插件将秘密吸收量及最大生命值直接交给 `StatusBar`，由游戏绘制填充。

`common.json` 保存固定启动字段 `锚点`、`职业`、`专精`。其余文件按英文职业名命名，例如 `Warrior.json`、`Priest.json`，每个文件包含：

- `keymap`：该职业使用的 keymap 文件名。
- `一键法术`：状态中的本地技能索引到 spellId 的映射。
- `一键物品`：状态中的本地物品索引到 itemId 的映射。
- 以专精 ID 为键的对象，包含普通状态与物品字段，以及可选的 `auras`、`spells`、`group`。

运行时先读取 `common.json` 确定职业和专精，再合并对应专精配置。`group.start` 是队伍数据起始列，`group.num` 是每名成员占用的列数；组内字段的 `step` 是相对偏移。
队伍配置可按专精勾选“职业”。勾选后插件为每名队友增加一个像素，写入与玩家职业相同的职业 ID（1–13）；未勾选时不占像素。实时队伍页显示职业名称和 ID，模块的队友筛选可用职业 `==`、`!=` 比较；没有采集到职业的成员不满足职业条件。

### `keymap` 与单位编号

每条 keymap 记录包含 `unit`、`技能`、`热键` 和可选的 `宏条件`。模块和 keymap 共用以下单位编号：

- `0`：无目标。
- `1`～`40`：队伍/团队槽位。
- `41`：玩家。
- `42`：当前目标。
- `43`：焦点。
- `44`：地面。
- `45`：鼠标指向。
- `46`～`50`：首领 1～5。
- `51`～`55`：竞技场单位 `arena1`～`arena5`。

当前映射版本为 `UnitMappingVersion = 4`。版本 1 模块会迁移旧的 `31/34` 含义；版本 2 模块中的 `36/37` 会迁移为 unit 0，并分别补成 `channeling` / `nochanneling` 宏条件；版本 3 的保留单位 `31`～`35` 会迁移到 `41`～`45`。生成的 keymap 同样携带映射版本，确保新版团队槽 `36/37` 不会被当成旧宏条件。

像素状态中的“目标类型/焦点类型”会把 `arena1`～`arena5` 编码为 `51`～`55`，“其他单位”使用 `56`；友方仍在基础编号上加 `100`。

## 模块系统

宏快照和 keymap 现按职业级动态宏处理；左右修饰键共 26 组、44 个基础键，屏蔽 1 个不可用组合后总容量为 1143 个槽位。

模块宏导入同样按职业级列表合并；历史模块中的专精动态字段只作兼容迁移，牧师/圣骑士合并后写入职业宏，其他职业丢弃。

模块以 `模块名.json` 保存在我的文档目录 `{MyDocuments}/Shigure/module`。名称不能重复；加载时会递归扫描子目录，以兼容旧版布局。模块页保存时会写入当前 Shigure 版本。版本不一致或为空的模块仍可把有效的依赖快照导入本地配置和宏，但不会参与模块选择和运行；编辑器列表中显示为红色，可在检查并显式保存后升级到当前版本。职业和专精均已指定时，模块还会携带该专精的 `ClassBlocks`（包括姓名板配置）、职业 `spellsList` 与 `itemsList`，以及该职业的职业级动态宏、静态宏和特殊宏。

启动和“刷新模块”会把模块携带而本地缺少的配置与宏追加到当前版本的插件目录。光环、姓名板光环、法术和技能列表都以 `spellId` 判断同一条目，不再按名称回退：光环任一 ID 重合即合并 ID 集合，`maxApps` 仅补本地空值，`isPlayer` 不同时保留本地并提示冲突；本地尚未启用姓名板而模块带有姓名板配置时，会创建姓名板配置并导入其光环。法术的布尔属性采用 true 补齐 false，最大充能和施法次数仅补本地空值；双方都有不同值时保留本地并提示冲突。技能列表快照不保存来源索引；同一 spellId 保留本地索引和名称，缺失 spellId 按模块快照追加，并自动分配当前职业 `1–255` 中最小的可用索引。索引已满时拒绝该模块依赖导入。物品冷却以 `itemId` 判断同一条目，`isEquipped` 用 true 补齐 false，空名称补齐，名称不同则保留本地并提示冲突；名称已被其他 itemId 占用或与状态字段重名则跳过追加。物品列表同一 itemId 保留本地索引和名称，缺失 itemId 按模块快照追加。队伍配置同样合并：保留本地字段顺序并追加缺少的状态字段，生命值与职责为必需字段；队伍光环按 spellId 合并 ID 集合和缺少的名称、maxApps，已有 maxApps 冲突时保留本地并提示。合并后的完整主像素布局（状态、光环、冷却、40 人队伍及姓名板）超过 1020 格时，拒绝该模块的全部配置和宏写入，并弹窗提示合并失败及所需格数。发生新增或补齐后会自动重建 `config/keymap`、同步游戏插件并按需重启运行。导入前会按每项动态宏 40 个槽位、静态/特殊宏各 1 个槽位检查职业级宏总容量；合并结果超过 1143 个槽位时，整个模块不会进入模块列表或运行时，本地 Lua 也不会被修改。模块文件仍保留在模块目录，调整配置或清理宏后可刷新重试。

模块匹配字段：

- `ClassId`：职业 ID。
- `SpecId`：专精 ID。
- `PartyType`：`0` 为单人、`1-40` 为团队、`46` 为队伍。
- `HeroTalent`：英雄天赋 ID。

任一字段留空（界面显示 `任意 (*)`）即为通配。多个模块同时匹配时，优先选择具体匹配字段更多的模块，相同则按名称排序。`RecommendedTalent` 仅用于说明，不参与匹配。

模块文件示例：

```json
{
  "Id": "戒律-20260730120000000",
  "Name": "戒律",
  "Author": "模块作者",
  "RecommendedTalent": "推荐天赋代码或说明",
  "Version": "1.2.1.31",
  "UnitMappingVersion": 4,
  "Enabled": true,
  "Match": {
    "ClassId": 5,
    "SpecId": 1,
    "PartyType": "46",
    "HeroTalent": 1
  },
  "Units": [],
  "Counts": [],
  "ValueAdjustments": [],
  "Rules": [
    {
      "Enabled": true,
      "Condition": "生命值 < 50 && spells.17.cooldown == 0",
```

规则按顺序判断，第一条命中的规则会执行。普通动作的 `Spell` 保存并使用“技能”列中的技能或宏名称，不用 spellId 判断；运行时按名称、目标单位和宏条件查找 keymap 热键。填写 `Hotkey` 时会直接发送该键。技能下拉还包含以下特殊动作：

- `暂停`：命中后不发送按键，并停止继续匹配本轮后续规则。
- `自动插入法术`：读取状态字段 `插入法术`，按职业配置映射到当前可用技能。
- `自动插入物品`：读取状态字段 `插入物品`，按职业 `itemsList` 映射到当前可用物品宏。
- `一键法术`：读取状态字段 `一键辅助`，按职业配置映射到技能。

### 条件

支持的常见表达式：

- 状态：`生命值 < 50`、`战斗时间 > 0`。
- 玩家光环：`auras.player.114255.value > 0`；层数使用 `.apps`。
- 目标/焦点光环：`auras.target.harmful.55078.value > 0`、`auras.focus.helpful.12345.value > 0`。
- 首领减益：`auras.boss1.harmful.55078.value > 0`（首领2–5分别使用 `boss2`–`boss5`）。
- 技能：`spells.633.cooldown == 0`；充能冷却和层数分别使用 `.chargeCooldown`、`.count`。
- 队伍：`group.1.生命值 < 60`。
- 列表：`目标类型 in (1, 2)`、`职业 not in (4, 9)`。
- 模块数组：在「动态数值 → 数组」中创建名称和数字列表，例如 `数组1 = { [123] = true, [456] = true }`；条件可写 `目标施法技能 in 数组1` 或 `焦点施法技能 not in 数组1`。数组按模块保存，编辑数字时自动显示 `SpellIcons.shgpack` 中对应的法术图标和名称；找不到法术资料的数字仍可保存。
- 敌人数量与敌人平均血量的筛选可选择姓名板“施法技能”（需在姓名板配置中启用）。可按原始 spellID 写 `== 123456`、`!= 123456`，或选择 `in`、`not in` 并引用本模块数组。无施法读数为 `0`；多个敌人按各自姓名板槽位独立匹配。
- 组合：`生命值 < 50 && spells.633.cooldown == 0`、`目标类型 == 1 || 首领战 > 0`。
- 字段间比较：`无痛敌人 <= 有效敌人数量`，比较符右侧除数字外还可以写另一个字段名。
- 布尔简写：`移动` 表示为真，`!移动` 表示为假。
- 空条件：始终命中。

`一键辅助`、`插入法术`、玩家分类的`施法技能`、`上个技能` 是技能列表索引状态。可视化编辑器为这些字段提供“技能图标 / 技能名称 / spellId”下拉；`==`、`!=` 与数组的 `in`、`not in` 均按 spellId 编写，运行时按当前职业的 `spellsList` 把 spellId 转换为本地索引后再比较，因此模块不依赖来源职业文件中的索引分配。找不到 spellId 时，单值条件按不命中处理。目标、焦点、首领和姓名板的`施法技能`直接返回原始 `spellID`，使用普通整数条件或模块数组。

`插入物品` 是物品列表索引状态。可视化编辑器提供“物品图标 / 物品名称 / itemId”下拉，并且只允许 `==`、`!=`；模块条件保存 itemId，运行时按当前职业的 `itemsList` 把 itemId 转换为本地索引后再比较。找不到 itemId 时同样显示为红色，条件按不命中处理。

生成的 `config/*.json` 和运行时状态使用“范围 + spellId + 数值类型”的结构化键；字段节点中的 `displayName`、`spellId`、`scope`、`metric` 和 `spellIds` 仅用于显示及别名解析。多 ID 光环优先使用单值 `spellId`，否则使用最小有效 ID 作为规范键，其余 ID 映射到同一运行时值。普通条件、子条件、动态数值、公式、动态单位和人数统计均持久化 spellId；缺失引用会保留原 ID、显示红色并按不命中处理。

字符串可以使用单引号或双引号。`true/yes/是`、`false/no/否`、`null/nil/空` 会转换为对应字面量。`&&` 的优先级高于 `||`，主表达式不支持括号嵌套。

规则还可添加多个“子条件”：主条件与子条件组是“且”关系，子条件之间是“或”关系，即 `主条件 && (子条件 1 || 子条件 2)`。这用于表达主编辑器无法用括号表示的逻辑。

可视化条件编辑器会按当前职业/专精提供状态、光环、冷却（技能/物品）和动态单位字段，并支持：

- 数字比较 `==`、`!=`、`>`、`>=`、`<`、`<=`。
- 文本/数字列表比较 `in`、`not in`。
- 数值字段的「值」列既可手填数字，也可从下拉中选择动态单位的数量、生命值或动态数值作为比较对象；右侧写成未加引号、能解析出数值的字段名时按该字段的当前值比较，否则仍按字面量处理。
- `延迟 (ms)`：限制同一规则两次实际发送的最小间隔。
- `逻辑延迟 (ms)`：发送后暂停模块规则计算指定时间；画面扫描、触发键检测和界面刷新仍继续。
- `继续逻辑`：本规则命中并发送后继续判断后续规则，后续命中也可再发送；直到遇到未设置继续逻辑的命中规则或列表结束。

缺失或非数字字段参与大小比较时视为不命中，不会中断运行。

### 动态单位、数量与动态数值

这些字段按 `group` 状态每帧重新计算。多数动态选择与数量统计会跳过 `职责 == 0` 的单位；具体生命值过滤取决于字段类别。

- 队友单位：与队友数量共用条件组列表筛选有效队伍单位，再按「查找的单位」选出唯一槽位。目标字段为生命值/治疗吸收时可选最低或最高；职责/驱散为正序或倒序（按队伍槽位）；光环可选最长、最短，或在拥有目标光环的队友中按队伍槽位正序、倒序，并须指定目标光环。可选「值名称」把所选单位的目标字段值暴露为同名数值条件字段。旧单位专用筛选字段不再迁移。队友单位可在规则目标中直接使用，也可用裸名称判断是否成功解析。
- 队友数量：使用条件组列表筛选有效队伍单位。每组可选“全部满足”或“任一满足”，组与组之间按“且”组合；条件支持生命值、治疗吸收、职责、驱散、职业及配置中的队伍光环。职责、驱散和职业只允许 `==`、`!=`，职业值从中文职业下拉选择；其它数值字段支持 `==`、`!=`、`>`、`<`、`>=`、`<=`。生命值、治疗吸收和光环的右值可手填整数，也可从下拉菜单选择公式动态数值的名称，或填写其它动态字段名。禁用行及没有启用行的空组会被忽略。该字段只能用于条件。
- 敌人数量：使用与队友数量相同的条件组列表，支持生命值、距离、战斗及配置中的姓名板光环；姓名板启用“仇恨值”后可按 `0–3` 状态进行数值筛选，关闭时该条件不满足。正式服奇袭启用姓名板强化锁喉时，还可筛选“强化锁喉”，仅支持 `==` / `!=`，值选择 `0=无锁喉、1=强化锁喉、2=普通锁喉`；关闭或未配置该字段时依赖它的条件不满足。生命值、距离和光环的右值可手填整数，也可从下拉菜单选择公式动态数值的名称。基础范围只包含存在且距离大于 0 的姓名板。光环 `== 0` 表示缺少、`!= 0` 表示拥有，其他比较仅在光环存在时判断，因此小于条件不会把缺少光环的单位统计进去。旧版专用数量筛选不再迁移或兼容。
- 平均血量：可选择队友或敌人作为统计对象，并与数量字段共用条件组列表筛选候选。队友基础范围为职责不为 0 的队伍单位；敌人基础范围为存在且距离大于 0 的姓名板。筛选后对剩余单位的生命值取平均（四舍五入为整数），无匹配单位时为 `0`。旧版卡片筛选不再迁移。
- 条件动态数值：条件成立时对已有状态、光环、技能或动态字段加减一个整数。
- 公式动态数值：使用字段和算术表达式生成命名数值，支持 `+ - * /`、括号、一元正负号和 `int`、`round`、`floor`、`ceil`、`min`、`max`。

动态单位和数量阈值既可使用固定值，也可引用其它动态数值。规则引用未解析出的动态目标时会跳过该规则，继续判断下一条。

模块 JSON 使用 `Units`、`Counts`、`ValueAdjustments` 保存这些定义；规则使用 `UnitName` 引用动态单位。名称不能是纯数字，不能包含 `.` 或 `$`，也不能与已有状态字段或其它动态名称冲突。

## 默认逻辑与 C# 扩展

如果没有匹配模块，`LogicRegistry` 会尝试使用按职业注册的 `IClassLogic`。当前没有注册项时会进入 `DefaultClassLogic`：仅当 `一键辅助 == 10` 且 keymap 中存在 `一键辅助` 时发送按键，否则显示“C# 职业逻辑尚未迁移”。

通常应优先在 `模块` 页维护逻辑。确实需要复杂算法时，可实现 `IClassLogic` 并在 `LogicRegistry` 中按职业 ID 注册：

```csharp
public sealed class PriestLogic : IClassLogic
{
    public LogicDecision Run(GameState state, string? specName)
    {
        var health = state.GetInt("生命值");
        return new LogicDecision(
            Hotkey: null,
            Step: $"当前生命值: {health}",
            UnitInfo: new Dictionary<string, object?>());
    }
}
```

职业逻辑可通过 `GameState.GetInt(...)`、`GameState.GetBool(...)`、`state.Auras`、`state.Spells`、`state.Group` 读取数据，并返回 `LogicDecision`。也可以创建匹配字段全部留空的通配模块，覆盖默认逻辑。
